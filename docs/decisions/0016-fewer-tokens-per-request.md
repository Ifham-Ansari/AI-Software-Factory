# 0016: Fewer tokens per request, and notifications that point to their screen

**Status:** accepted · 2026-11-22

**Context.** Every request of a run resends the agent's instructions and its conversation. Measured on a real project on the built-in engine, the instructions were about 10k tokens: the Tech Lead's skill carries all eight of its modes (80% of the skill), though a run does one. A long plan run sent 2.45M tokens over 115 requests, and the history was sent whole until a request no longer fitted. Then compaction stubbed everything but the last six results, so runs swung between sending everything and almost nothing. In the same project, notifications were mostly noise: each blocked task produced two ("P-001 is blocked" and a generic "AI Software Factory needs your attention" from the alert raised with it), 22 of 28. The unread count only cleared with "Mark all read", and nothing showed which screen a notification belonged to.

**Decision.**

* **Instructions for one mode.** `buildSystemPrompt` takes the run's mode and keeps only that `## Mode:` section of each skill, plus the sections every mode shares. The others become one line that names them and the skill file. A skill without a section for the mode (the engineers', or a mode a skill does not describe) is kept whole, and headings inside code blocks do not count. The short instructions point at the run's section instead. Mode sections must stand on their own: the Tech Lead's answer mode now spells out the invariant test instead of pointing "above" to architect mode. The system prompt is now identical per role and mode, not per role. Claude Code's prompt cache still covers almost every build run (they are all `implement`), and planning modes rarely ran close enough together to share it.
* **Old tool output trimmed on every request** (built-in engine). `trimStale` (core) runs before compaction on each request. Results older than the latest six that are longer than 300 characters keep their first line and a note, and calls that already ran lose big arguments (written content is on disk). Trimming moves four results at a time, so consecutive requests share the same start, which providers with automatic prompt caching reuse. With the short instructions, the latest read of each SKILL.md stays whole, because it is the agent's instructions. With the full instructions, reads of skills are trimmed like other files, since the skills are already in the system prompt. A first version that kept every skill-file read made the longest run worse: a model on the short instructions had read the skills, and a later model on the full instructions carried them twice.
* **One notification per blocked task.** An alert raised for a task that is blocked at that moment is marked `taskBlocked` and makes no notification of its own; the block already did, and the alert still lists the details under Questions & alerts. Other alerts are titled with their first sentence ("Usage limit reached"), the rest as the body.
* **Read state per notification, and highlighted tabs.** The dashboard keeps the ids of notifications read one at a time, next to the "mark all read" mark. Opening a notification (toast, bell, or desktop) marks it read. Looking at a screen marks its notifications read, but not while the browser tab is in the background. Each sidebar tab with unread notifications gets a tint and a dot on its icon in the color of the most important one (needs you, warning, done, info), pulsing for the first two, plus "N new" for screen readers.

**Consequences.** On the project's real conversations, the two longest planning runs send 25% and 31% fewer tokens (2.45M to 1.84M, 1.49M to 1.03M), and every long run 15% to 21% fewer from the trimming alone. Engineers' instructions are unchanged (their skills have no modes); their long runs gain from the trimming. An agent that needs an old result in full runs the tool again, which costs one turn; six recent results stay whole for the usual read-then-edit steps. Skills must keep each mode self-contained. The owner sees one notification per event and can tell where to look from the sidebar.
